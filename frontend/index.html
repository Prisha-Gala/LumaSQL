Bring your own data

Upload CSV, a JSON array of objects, or a SQLite database. Add multiple tables to the same dataset to explore joins.

Without a schema, types are inferred. SQLite tables and supported indexes are imported together. Max 8 MiB per request; 30,000 rows per table.

Your SQL toolkit

Use SELECT, DISTINCT, FROM, aliases, INNER JOIN … ON, WHERE, AND / OR / NOT, comparisons, arithmetic in conditions, IS NULL, ORDER BY and LIMIT.

Aggregates, GROUP BY, subqueries, outer joins and data-changing statements are outside this version's supported SQL subset.

Cost units ≠ milliseconds. Scan and join costs are model estimates. Execution timings are measured separately. Index creation is a one-time setup cost. This project executes its own physical plans; it does not claim to outperform a production database optimizer.

Syntax mode needs no tables. Compile mode validates against real tables and builds a plan. Execute mode also runs that plan and compares the full result with the baseline.

How LumaSQL works

LumaSQL is an educational optimizing SQL compiler. It turns a SELECT statement into an executable query plan, then uses its own Python operators to return rows. You can inspect each compiler phase and compare the work before and after optimization.

Use the website

  1. Choose the demo dataset, or import CSV, JSON or SQLite tables into one dataset. Inspect the schema and indexes in “Set the scene”.
  2. Enter SQL or choose a sample. “Compile & execute” runs all seven phases; “Compile only” builds a plan without executing; “Check syntax only” runs phases 1–2 without a dataset.
  3. Start the journey. Each “Run phase” button makes a backend request for that next phase. Revisit completed phases in the sidebar. The submitted query stays visible on each phase.
  4. Compare the code and rule changes in Phase 5, then costs and physical strategies in Phase 6. Phase 7 shows results, baseline-versus-optimized measurements and verification.
  5. Download the run report, generated code, SVG tree or displayed result CSV. “Back to editor” lets you change the query or data.

The seven phases

  1. Lexical analysis: SQL text → keywords, identifiers, literals, operators and punctuation.
  2. Syntax analysis: tokens → AST, checking the supported grammar.
  3. Semantic analysis: AST + schema → resolved aliases/columns and checked types.
  4. Intermediate code: bound AST → intermediate instructions using temporary relations.
  5. Rule optimization: equivalent rewrites simplify expressions, move filters and prune columns.
  6. Cost optimization: statistics guide sequential/index scan and nested-loop/hash join choices.
  7. Execution: run the selected plan, collect work counters and compare the full result with the original plan when verification succeeds.

How the parts connect

The browser uses plain HTML, CSS and JavaScript. A local Python HTTP server serves the site and compiler/data APIs. The catalog stores imported tables, column types, frequencies and in-memory equality indexes. The compiler validates SQL, creates plans, optimizes them and executes its own operators. Data persists in data/catalog.json; journeys live in memory until the server restarts.

SQLite is an import format, not the query engine. Final code panels serialize relational plan objects; this project does not emit rewritten SQL or machine code. Costs are estimated work units, while Phase 7 timings are measured milliseconds. This small model retains SQL join order and supports the SELECT subset listed in the SQL guide.
